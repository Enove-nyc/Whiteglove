# The two scans of 27 August 2026 — checked, one by one

Two documents arrived the same day: a full-site design rescan and a three-app
audit. This file records **what was checked, what was true, and what was not**,
because an audit read as a task list is worth less than an audit read as a set
of claims — some of these were right and are now fixed, some were right and are
open, and three were wrong.

Everything below was verified against the running site or the code on
27 August 2026, in a real browser at 390×844, 768×1024 and 1280×900 where the
claim was about layout. Where a claim did not reproduce, the measurement that
replaced it is given. Check again before acting: this file will go stale like
every other one here.

## Fixed on the day

**The sample itinerary was cut off on a phone and a tablet.** True, and the
scanner's numbers were exact: 816px sheets inside 375px and 753px content
areas, running to x=849 and x=873. The page did not scroll horizontally — it
was clipped, so the corner arc, the right edge of the times column and part of
every day's header were simply gone. This is the one public piece of evidence
for what the product produces. Below 900px the sheet is no longer a sheet:
full width, ordinary padding, paper decorations dropped, the inch-measured
timeline and cover summary stacked, and the smallest print type lifted to phone
sizes. Print and desktop are untouched. Both repositories.

**The itineraries `/app` carried a Kosher Travel browser title.** True. It was
the tab, the bookmark and the link preview of the page a client opens from the
link their advisor sent. `pageMetadata` settles the site name from the title
string, so the three pages whose titles named neither brand fell back to the
kosher one. All three now read the host. The guard test that should have caught
it was a list somebody had typed, written from the pages the marketing journey
touches — which is exactly why it covered `/login` and `/plan` and missed the
three pages a client opens. It now derives its list by scanning `app/`.

**`/stops` answered on the itineraries domain under a kosher title.** Found
while fixing the above, not reported by either scan. It is the kevarim-towns
directory and had never been on `GUIDE_ONLY_PREFIXES`, so it rendered instead of
redirecting.

**The pricing introduction promised what its own table takes back.** True. It
said the planner and "sharing a trip with anybody you like" is the same on
every plan; the feature table says handing a client their own app is an advisor
plan. Both described something real — a share link, and `companionClients` —
under one word, in the paragraph a buyer is deciding on. It now names the
planner, the map and the guides.

**The sitemap dated all 804 URLs to the moment the crawler asked.** Reported as
P2 "misleading freshness signals"; worse than that in fact. `lastModified` was
computed on the handler's first line under a comment claiming it was the build,
but the route reads Redis and is therefore dynamic. Every fetch stamped the
whole site as changed since last night. A crawler told that stops reading the
field, and the pages that really did change lose their only signal. It is now
computed at module scope — the deploy, which is what the comment always meant.

**The hechsherim page said each agency's name three times.** Not the reported
finding, but found underneath it — see below.

## Did not reproduce

**"All 271 certification images on `/hechsherim` lack meaningful alternatives."**
The count is right and the conclusion is wrong. Every one of those images sits
inside a container marked `aria-hidden="true"`, so a screen reader never reaches
the `alt` at all; the agency is named in text beside it. An empty `alt` on a
decorative image is the correct markup, and giving each one "Orthodox Union OU
certification mark" as the scan recommends would add a fourth announcement of a
name already said three times.

Which is the defect that was actually there. The badge printed its own visible
label *and* its own screen-reader sentence next to a row that already had the
agency's name, so every row showed "Hechsher: Orthodox Union" beside "Orthodox
Union" and read the name three times aloud, 271 times down the page. The badge
now takes a `decorative` flag for the two places that draw the mark beside the
agency's own name. It defaults off, because on a listing the badge is the only
thing naming the hechsher.

**"Rome rendered 12 empty H3 elements; London and Paris rendered 11 each," and
"several links with no accessible text."** Measured in a real browser at 390px
on all three pages, plus `/tzaddikim`, `/destinations`, `/hechsherim`,
`/mikvaos`, `/cemeteries` and `/stops`: **zero empty headings and zero unnamed
links on every one of the nine.** Rome has 36 headings and 62 links, all named;
London 148 and 58; Paris 33 and 55.

The scan says the pattern is in the reusable destination template and therefore
affects most of the 21 destination pages. It is not in the template. The most
likely explanation is headings counted inside collapsed `<details>` elements, or
a measurement taken before hydration finished. Worth re-running with the
selector and timing stated, because if there is a real case behind this it is
somewhere the nine pages above do not cover.

**"The itinerary app's browser title"** — fixed, but note the scan itself
observed that the repository already contained a host-aware fix and inferred a
deployment gap. It did not: the fix covered other pages and had never covered
these three. The inference was reasonable and the conclusion was wrong, which is
worth saying because "the code is right, the deploy is stale" is a comfortable
answer that stops the search.

## Also fixed, the same day

**The long directories.** Confirmed almost exactly and then cut, measured at
390px in a browser:

| Page | Before | After |
|---|---:|---:|
| `/tzaddikim` | 70,685px | 20,311px |
| `/destinations` | 53,418px | 10,042px |
| `/hechsherim` | 39,211px | 7,176px |
| `/mikvaos` | 19,948px | 16,767px |

`CappedGrid` opens a list on its first screenful and offers the rest on one
press, hiding the overflow in CSS rather than dropping it from the markup — so
all 406 kever links and all 156 destinations are still in the HTML a crawler is
served. Three sizes chosen by the call site, because one was wrong in both
directions at once. `/hechsherim` needed the cap one level up as well, and
needed a search box, which was the real defect there: the page exists for
somebody holding a package with an unfamiliar mark and answered that by printing
287 agencies under 81 headings with no way to look one up. `/cemeteries` was
left alone deliberately — it already pages against the server.

**No public demonstration of the client app.** `/app/preview` renders the demo
trip that was already in the repository and already the component's own default,
used for nothing. Labelled as a sample above the fold, linked from `/app` beside
the code field, noindex, no advisor inbox.

**The client app's small controls.** Eight of them — the document-share toggle
and the note actions the audit named, plus "Full day", the chat's Cancel, the
quick replies and the place-share submit — now carry a 44px hit area through
padding with an equal negative margin, so each looks exactly as it did.

**The role boundary has tests.** Not the split both audits recommended, which is
weeks of regression risk on a working screen for no visible change, but the
other half of the same recommendation: every use of `WalletShareToggle`,
`WalletAttach`, `GuideNoteEdit` and `AdvisorAlertComposer` is checked for its
`!isClientViewer` guard, with the consequence named. Confirmed to fail when a
guard is removed.

## Found while working, not by either scan

**`/advisor` returned a 500 on every request.** The paid advisor dashboard on
the itineraries domain threw `Attempted to call advisorPlacesFor() from the
server but advisorPlacesFor is on the client` — a pure function living in a
`"use client"` module, imported by a server component. `tsc` passes, `next
build` passes, and the page is behind a login, so nothing automated reached it.
The owner found it by opening his own dashboard. `tests/server-client-boundary.test.ts`
now reads every server page, layout and route in both repositories and fails if
one imports a plain value out of a client module.

**The itineraries repository had a 44-error lint backlog** the kosher one had
already cleared and never had ported — including two config decisions and a
`prefer-const`. Most of the 35 hook errors were visible defects as well as rule
violations: a pop-up painted once still open over a save that had gone through,
a client's already-read alerts flashing as new, a flight form showing an empty
date after it had been filled in. Zero now.

## True and still open — all three blocked on something other than code

**Record-level freshness.** No last-checked date beside individual records. The
honest obstacle is that there is no per-record "when was this checked" to
print — `lib/data-health.ts` reports how much of the database has never been
positioned or filled in at all. A date field with no date behind it converts
"we do not know" into "we checked", on kashrus and cemetery access information.
This needs the data collected before it needs an interface, and it is not a
front-end defect.

**The homepage repeats one default image.** True and deliberate:
`lib/default-photo.ts` stands in wherever a section has no picture, rather than
a blank box. Replacing it needs licensed photography per category, which is a
purchasing decision.

**`google.maps.Marker` is deprecated.** `components/AreaMap.tsx` uses it.
Moving to `AdvancedMarkerElement` requires a Map ID created in the Google Cloud
console — an account action, not a code change — and Google has committed to
twelve months' notice before removal.

## Declined, with reasons

**Splitting `ItineraryBuilder.tsx` and `CompanionApp`.** See above: the tests
protect the invariant the recommendation was worried about, without the
refactor.

**"Four navigation systems at once on mobile."** A design judgement rather than
a defect, and one that touches every page. Not something to change from an audit
line without the owner asking.

## What neither scan could check

Both say so themselves, and it is the honest limit. The advisor workspace and a
real client trip are behind a login and a per-trip share token, so both scans
read the architecture from the repository and inspected only the public shell.
Every claim about what an advisor or a travelling client actually sees —
offline behaviour, timezone handling across a date line, payment receipts, chat
context, traveller-level redaction between two people on one group trip — is
unverified by either document, and is not verified here either.
